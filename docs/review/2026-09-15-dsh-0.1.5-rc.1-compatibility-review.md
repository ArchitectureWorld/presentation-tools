# 2026-09-15 — Report Studio / DSH 0.1.5-rc.1 Compatibility Review

## Scope

Target repository: `ArchitectureWorld/presentation-tools`  
Target branch: `feat/report-studio-v0.2.0-layout`  
Report Studio: `0.2.0-alpha.3`  
Plugin package: `@architectureworld/report-studio-dsh@0.1.1`  
Target DSH: `0.1.5-rc.1`  
Node baseline: `>=24.11.0`

Historical acceptance and handoff records keep their original version facts. This document is the current compatibility review for the active v0.2.0 layout branch.

## Current conclusion

DSH 0.1.5 introduced **two material compatibility breaks** for Report Studio:

1. the Web Client composition removed the legacy `@deepseek-ai/dsh-client-runtime` package in favor of domain-scoped Client/API packages;
2. the Host composition removed `@deepseek-ai/dsh-host-apiproxy`, so a hard `apiProxy` Cordis injection leaves the plugin pending and unable to activate.

Both have now been migrated on the active branch. Report Studio does not introduce a second Agent runtime: DSH remains the only Session, model and Agent authority.

The following integration points remain valid and are retained:

- Host `ctx.sessions` and `SessionHeader.cwd`;
- Host `sessionController`, `sessionProjections`, `agentDefaultModel` and `llm`;
- Cordis `session/event` and `session/disposed` events;
- tool execution `exec.agent` identity, not removed `ctx.agent`;
- Client `ctx.sessions`, `sessions.binding(sessionId)` and `session.prompt(content, 'queue')`;
- `conversation.view` and `conversation.session.header.actions` slots;
- loopback-only `/report-studio` Host `webServer` route.

Report Studio no longer reads the removed `session.events` array. Session V3 changes DSH migration and rollback operations, but does not require a Report Studio Repository schema migration.

## 2. Host service correction: `apiProxy` removed

The earlier assumption that `apiProxy` might remain available in DSH `0.1.5-rc.1` was incorrect. The released Web composition does not provide `@deepseek-ai/dsh-host-apiproxy`; therefore this old injection is invalid:

```js
['tools', 'webServer', 'systemPrompt', 'sessions', 'llm', 'apiProxy']
```

Current Host injection is:

```text
tools
webServer
systemPrompt
sessions
llm
sessionController
sessionProjections
agentDefaultModel
```

The isolated review worker resolves the parent Session model through the 0.1.5 Session Controller state:

1. use `ctx.sessions.get(parentSessionId)` when live;
2. use `ctx.sessionController.resolveAgent(parentSessionId)` when the Session must be resumed;
3. read `ctx.sessionProjections.snapshot(session).values.modelSelection?.next`;
4. fall back to `ctx.agentDefaultModel.currentSelection()`;
5. execute the isolated worker through `ctx.llm`.

Static verification now rejects any reintroduction of `apiProxy` into active deployment code or compatibility metadata.

Commit `cbc59d9fb4d4cc3c5cde2173efd1e7abaad1aff0` reached a real DSH `0.1.5-rc.1` Web startup with `@architectureworld/report-studio-dsh` composed. That proves the original `pending (waiting for service: apiProxy)` activation blocker is removed.

## 3. Session V3

The old `session.events` array is not used. Native review recovery now uses:

```text
session.seq
session.snapshotEvents()
session/event
session/disposed
```

Before first opening an existing DSH home with `0.1.5-rc.1`:

- stop all DSH processes;
- cold-backup the complete `DSH_HOME`;
- keep Report Studio data backup separately;
- do not treat package downgrade alone as Session rollback;
- avoid first V3 migration directly on exFAT, unreliable FUSE mounts, or network/NAS paths without local filesystem semantics.

Report Studio A1.1 migration remains independent from DSH Session V3 migration.

## 5. DSH 0.1.5 browser authentication

DSH 0.1.5 protects the complete Host API with browser-session authentication. On startup it emits a one-time root URL of the form:

```text
http://127.0.0.1:<port>/?token=<launch-token>
```

The launch token is accepted only by the root page to establish the signed HttpOnly browser cookie. It is not an API bearer token and must not be copied into an Authorization header or API URL.

The native smoke therefore must:

1. capture the startup URL without printing the secret;
2. request the tokenized root with redirects disabled;
3. retain only the returned browser-session cookie;
4. use that cookie for Session/API requests;
5. preload the same cookie into the real Chromium context before verifying the DSH Web Client;
6. redact the launch token from CI logs and errors.

The first real target smoke after the `apiProxy` fix started DSH successfully but received `HTTP 401: unauthorized` at Session creation because the old smoke harness skipped this token-to-cookie exchange. That failure is a smoke authentication defect, **not** a Report Studio activation failure.

## 6. Security boundary

No compatibility evidence justifies relaxing the existing deployment model:

- `securityMode=local-single-user-only`;
- DSH Web listener remains `127.0.0.1`;
- query `sessionId` is a local routing key, not authentication;
- DSH browser-session authentication remains authoritative for the Host API;
- Report Studio does not claim supported network-shared deployment.

## 7. Compatibility gates

Static verification rejects:

- `@deepseek-ai/dsh-client-runtime` in active deployment files;
- `apiProxy` in active Host dependencies;
- removed Host `ctx.agent`;
- removed Session `session.events`;
- DSH baseline drift from `0.1.5-rc.1`;
- Node baseline drift below `24.11.0`;
- Web Client graph drift.

Target smoke must prove:

- exact DSH CLI version;
- plugin present in composed `--dump-config`;
- real Web Profile boot with the plugin active;
- DSH browser authentication exchange;
- Session creation/resume;
- Report Studio health route;
- production UI and native browser bridge;
- real DSH Web Client requests the Report Studio client bundle without composition errors.
